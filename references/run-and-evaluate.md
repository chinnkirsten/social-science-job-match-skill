# 运行、增量更新与效果验收

## 每份报告独立保存画像

本地任务记录保存招聘模式、意向城市、毕业时间、全职入职时间、薪酬硬下限、用户已确认偏好与未知项。用户明确目标优先；“全职”本身不能区分校招与社招。已有答案不重复询问。不同候选人分别建目录，私人记录不入Git。

先读少量具体JD验证方向和资格，再扩大搜索。先筛招聘模式、城市、届别、硬条件；通过后才生成逐岗简历建议。每份报告按需选择工具，工具注册表不要求全量加载。目标仍为20家合格公司；命中不足时披露缺口，不能静默减量或放宽条件。

## 中国校招专项核对

应届校招逐项保存：招聘批次与年份、毕业起止日期、全职入职日期、专业限制、学历要求、既往劳动关系或社保限制、国内/境外毕业时间差异、资格证书及申请截止口径。每项写雇主原文与来源；未披露的写未披露。此清单是核对问题，不代表所有雇主都设置这些条件。

把原文条件转为requirements时保留“或”“优先”“入职前取得”等逻辑。既往两年工作经历不自动判定失去校招资格，也不自动认定仍有资格。简历中有实习经历不改变当前校招全职目标。财务、审计等岗位按候选人真实背景设方向，不因Skill名称中的“社科”自动排除。

## 缓存与断点续跑

缓存保存原JD文本、实际采集时间、内容指纹、原始URL及岗位编号。`captured_at`只能在重新读取原文时更新；报告生成时间不能冒充采集时间。

任务状态依次为：discovered → extracted → qualified → mapped → reviewed。状态转移要有对应证据；下载完成不自动成为已审核。中断后读最近一次完整检查点，保留失败原因和未完成岗位，使用临时文件写完后原子替换检查点。

- 原JD文本未变：复用提取与技能映射；交付前仍复核开放状态。
- 原JD文本变化：重新提取条件、重新判断资格、重做受影响的改写。
- 候选人证据变化：复用公开JD，重新计算资格与改写，不能复用另一个候选人的结论。
- 城市、模式或届别变化：重新筛选候选池，已抓原文仍可作为历史缓存。
- 检索失败：保留错误及时间；不把403或网络失败当作关闭。多次无新增有效岗位时调整授权范围内的检索词和来源，记录排除原因。

自动实现见`jobmatch_runtime/cache.py`与`pipeline.py`。保存命中数、重新读取数与模型调用耗时；24小时内同画像、同账本、同配置的完整检查点可跳过抓取与模型调用。当前实现按整个岗位检查点恢复，不承诺跨画像或单角色细粒度复用；改变配置须用新的运行目录。缓存命中不刷新原采集时间。私人缓存默认关闭，但检查点与报告本身仍含私人分析，始终存于仓库外受限目录。

## 语料与报告共用数据

岗位JSON嵌入`corpus`原始记录及候选人证据账本。`validate_jobs.py`会重算语料统计、核对来源和证据引用；不要另造一份汇总数字过检查。报告生成器读取这份已经通过审计的JSON，首页、清单和详情使用同一岗位ID。

Word自动生成器为`jobmatch_runtime/report.py`，执行顺序见[runtime-guide.md](runtime-guide.md)。它依照report-standard.md排版，逐岗包含JD和修改建议；机器草稿不能冒充人工确认稿。生成后仍须逐页渲染。交付正文区分可直接使用、核实后使用、完成作品后使用的改写，不因为引用编号存在就免除语义审查。

## 效果验收

当前回归测试使用模拟资料，仅证明特定错误会被拦截。真实效果评估必须使用获准用于本次工作的简历和有日期的公开JD，不把原文件加入GitHub。评估至少覆盖本科实习、硕士秋招、社招、有既往工作经历的应届申请者、硬条件不满足、原始经历不足等场景。

每场景由审阅者先标注合格/不合格/未知、JD条件出处、允许改写的经历，再运行Skill对照。分别记录：错误纳入、错误排除、未知项误判、虚构经历、证据漏引、重复岗位、坏申请链接、用户准备成本，以及耗时。错误纳入与虚构经历属于必须修复的问题；不要用一个综合高分掩盖。

先验证“简历→具体JD→资格→改写→Word”一条完整链路，再评价不同工具带来的提升。真实场景未跑过，必须写未实测，不把模拟测试次数当作服务效果。
